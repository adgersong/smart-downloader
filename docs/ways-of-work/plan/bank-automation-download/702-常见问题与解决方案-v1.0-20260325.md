## 🛠️ 常见问题与对应解决方案

### 1️⃣ 代码规范
**症状**：代码风格不统一，CI 报错 `flake8`/`eslint` 等。
**解决方案**：
- 在项目根目录添加 `pre-commit` 配置，包含 `ruff`, `eslint`, `stylelint` 等。
- 统一 `.editorconfig`、`pyproject.toml`（Python）或 `tsconfig.json`（TS）中的规则。
- 强制在 PR 阶段通过 GitHub Actions 运行 `lint`，不通过即阻止合并。

### 2️⃣ 硬编码
**症状**：代码中出现 `http://xxx/api`、`123456`、`/var/log/app.log` 等。
**解决方案**：
- 抽取为配置文件（`config.yaml`、`.env`），并使用 `python-decouple`、`dotenv` 或对应语言的配置加载库。
- 对于密钥使用 Secrets Manager（如 GitHub Secrets、Azure Key Vault），不直接写入源码。
- 引入 `constants.py`（或 `constants.ts`），统一管理魔法数字，并写上注释来源。

### 3️⃣ 日志 & 错误处理
**症状**：仅使用 `print()`，异常捕获后沉默或直接 `raise`，缺少统一日志结构。
**解决方案**：
- 使用结构化日志库（Python `loguru`/`structlog`，Node `pino`）统一日志格式（时间、级别、上下文）。
- 在全局捕获 `Exception`，记录堆栈并返回统一错误响应。
- 为业务关键路径加入 `error_code`，便于监控告警。

### 4️⃣ 依赖安全
**症状**：`requirements.txt` 中未锁版本，未执行安全扫描。
**解决方案**：
- 使用 `uv` 或 `pip-tools` 锁定 `requirements.txt`（`uv pip compile`）。
- 在 CI 中集成 `dependency-auditor`、`safety` 或 GitHub Dependabot，自动审计每次 PR。
- 对于 Node 项目使用 `npm audit` / `pnpm audit`，并设置安全阈值（high/critical）阻止合并。

### 5️⃣ 测试覆盖
**症状**：核心业务缺失单元测试，覆盖率低于 80%。
**解决方案**：
- 引入 `pytest` + `coverage`（Python）或 `jest` + `cobertura`（TS），在 GitHub Actions 中强制 `coverage > 80%`。
- 为每个新功能编写测试驱动（TDD），使用 `tdd-guide` 中的脚本快速生成模板。
- 对关键交互使用 E2E（Playwright / Cypress），放在 `e2e-testing-automation` 目录。

### 6️⃣ CI/CD 配置
**症状**：CI 步骤冗长、未缓存依赖、构建时间过长。
**解决方案**：
- 使用 `github-actions-templates` 中的缓存模板，对 `node_modules`、`~/.cache/pip` 进行缓存。
- 在工作流中加入 `pre‑commit` 步骤，确保代码在提交前已通过本地检查。
- 将部署脚本与单元测试分离，使用矩阵并行运行。

### 7️⃣ 文档缺失
**症状**：函数/类缺少注释，README 与实现不同步。
**解决方案**：
- 强制 `docstring`（Python）或 JSDoc（TS）并通过 `pydocstyle` / `eslint-plugin-jsdoc` 检查。
- 在 `docs/` 中维护文档索引，新增文档后自动更新（可使用 `mdx` 脚本）。
- 使用 `technical-writing` 技能生成统一的文档模板。

### 8️⃣ 配置管理
**症状**：不同环境（dev、staging、prod）配置混杂，手动修改导致错误。
**解决方案**：
- 使用 `environment-setup` 将环境变量写入 `.env.{env}`，并在启动脚本中自动读取对应文件。
- 对敏感信息使用 Secret Manager，在 CI 中注入 `ENV_` 前缀变量。
- 将配置验证放在启动前检查（如 `python -c "import config; config.validate()"`）。

### 9️⃣ 运行时异常（资源泄漏）
**症状**：文件句柄、数据库连接、线程未关闭，导致 Memory Leak。
**解决方案**：
- 用上下文管理器（`with open(...) as f`）或 `async with`，确保资源自动释放。
- 对数据库使用连接池，并在请求结束时调用 `close()`。
- 引入 `resource-leak-detector`（如 `tracemalloc`）在本地运行检测。

## 📌 落地建议
1. **统一代码检查**：在根目录创建 `.pre-commit-config.yaml`，加入 `ruff`, `eslint`, `markdownlint`，并在 CI 中执行 `pre-commit run --all-files`。
2. **配置中心化**：所有硬编码迁移至 `config/` 目录，使用 `python-decouple`/`dotenv` 读取。
3. **日志标准化**：在 `smart-downloader/backend` 与 `frontend` 共用 `logger.py`（或 `logger.ts`），统一 JSON 输出。
4. **安全审计**：在 `github-workflows` 中加入 `dependency-auditor` 步骤，发现高危依赖即阻止合并。
5. **测试覆盖门槛**：在 `ci.yml` 中加入 `coverage run -m pytest && coverage report -m --fail-under=80`。
6. **文档同步**：每次 PR 添加或修改代码，强制更新对应的 markdown 文档，并在 PR 描述中勾选 “文档已更新”。

> **参考**：本统计基于 OpenCode 项目过去三个月的代码审查记录、CI 报告以及 `grep` 关键字搜索，旨在帮助团队快速定位并统一治理常见技术债务。
